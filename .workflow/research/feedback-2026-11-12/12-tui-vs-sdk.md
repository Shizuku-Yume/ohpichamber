**Short answer:** title and recap are generated inside `AgentSession`, and the TUI only renders them. Next-prompt suggestion is split. The generation primitive (`AgentSession.runEphemeralTurn`) is SDK, but the trigger, prompt, parsing and ledger entry live in a TUI controller. So nothing hands us a suggestion. We have to drive it ourselves, and today our driver is a different, slower pipeline.

`OMP/` = `packages/agent-service/node_modules/@oh-my-pi/pi-coding-agent/src` (installed 18.18.0). `TUI/` = `…/pi-tui/src`. `~/Project/oh-my-pi` is 18.8.9 with the same layout, so I cited the installed copy. ## Why our suggestion is slow (item 15)

**TUI path:**
- `agent_end` with state `done` triggers `ComposerPredictionController.request()` immediately (`event-controller.ts:2662`).
- It is skipped if the user stopped the run, a draft exists, the session is streaming or compacting, or a subagent is focused. The setting is off by default (`composer.predictions=false`).
- It calls `session.runEphemeralTurn` with:
  - the **session's own model**, with the same system prompt, tools and history, so it reads the prompt cache;
  - `minimizeEffort: true`;
  - `maxTokens: 1024` only where `ephemeralMaxTokensPreservesRequest()` is true;
  - a 15 s deadline.
- The prompt is `composer-prediction-user.md`: reply with one line, or up to 4 lines with `predictionAlternatives`, or `NO_PREDICTION`.
- The reply is parsed and painted as ghost text. There is no timer and no persistence.

**Our path (`session-assist/runtime.js`), in sequence:**
1. On `run.completed` or idle status, `evaluateTurn` runs (`session-work/runtime.js:203`). If a Jev classifier endpoint is configured, that is an extra network call plus a history read.
2. A fixed **60 s quiet timer** (`IDLE_QUIET_MS = 60_000`, runtime.js:31). It is not overridden at `server/index.js:905`. This alone puts the floor at a minute. It is a leftover from the OpenCode design.
3. `sessionService.open` and paged `history` over HTTP to the Agent Service. `describeSmallModel` follows, using a catalog cached for 30 s.
4. `generateSmallModelText` is a **stateless `completeSimple`** (`worker/completion.ts:85`). It uses role `smol` (so it can land on a different model or provider than the session), a fresh prompt of up to 32k characters, a JSON-object output contract, and a reasoning level taken from the role. It has no session id or cache key, so there is no prefix cache. It has a 120 s timeout.
5. A re-read of history and `open` to check the answer is still current, then `persistSessionMetadataPatch` (a disk write).
6. The client sees the result only after the metadata change propagates and `getCurrentSessionAssist` passes the `generatedAt >= turn end` check, while the session is settled.

So we add a 60 s wait, 4–5 HTTP and disk round trips, and an uncached, larger, structured request on another model. The TUI sends one cache-warm request on the session model right at turn end.

## Decisions for the maintainer

1. **Suggestion engine.** I recommend a native driver in the worker, mirroring `enableIdleMaintenance`. At a `done` `agent_end`, call `runEphemeralTurn` with the same arguments as the TUI.
   - Reuse the exported `parseComposerPrediction(s)` and `composer-prediction-user.md`.
   - Record usage with `appendModelUsage({purpose:'composer-prediction'})`.
   - Emit a transient `session.suggestion` event like `session.recap`.
   - Delete the Host suggestion path.
   - Alternatives: (b) keep the Host path and drop the 60 s timer and Jev gate; it stays uncached and off the session model. (c) Keep it as is.
   - The native driver also needs a GUI setting, since `composer.predictions` is currently hidden as tui-only. The setting costs an extra billed request per turn, so decide the default.
2. **Titles.** Keep the worker-owned title for credential pinning, but start it while the first reply streams, or reuse `runEphemeralTurn` without cards.
3. **Plan mode and slash commands.** These are the two largest sources of drift. OMP exposes no non-TUI entry point for plan mode or for the 42 TUI-only commands. Either keep the mirrors and add an upgrade-time test against the pinned package, as `toolPresentation` does, or ask upstream for an RPC controller like `RpcGoalController`.
4. **Edit preview.** Forward `tool_stream_update.update` into the tool part (a new field in the contract). Then the UI can render live diffs.
