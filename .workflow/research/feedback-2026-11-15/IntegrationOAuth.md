## 1. Findings

### F1 (blocking) — An unauthenticated install is reported as an **error**, not "sign-in required". Confidence: high (code) / medium (which exact string the maintainer saw).

The classification exists, but only one of the two apply paths uses it.

- `configureMcpNow` commits the new revision, then applies it: `packages/agent-service/src/supervisor/catalog.ts:468-482` (`commitMcp` at `:474`, `applyMcpNow(..., true)` at `:482`).
- In `applyMcpNow`, classification of the failure **does** map auth to `saved-needs-auth` (`catalog.ts:529-538`) — but only when `status` is `failed`/`partial`, i.e. **when at least one live session worker exists**. With **no active worker** the branch is `status === 'no-active-workers' → unattendedMcpOutcome` (`catalog.ts:529`, `:914-925`).
- `unattendedMcpOutcome` runs the **stateless probe** and returns `saved-needs-auth` only when the probe's error code is **exactly** `MCP_AUTH_REQUIRED` (`catalog.ts:914-925`). Any other code → `saved-not-connected`, and `isConfigure && outcome === 'saved-not-connected'` **throws** `503 MCP_APPLY_FAILED` (`catalog.ts:543-545`).
- The probe's code comes from a **string regex** on the transport error, `isAuthError()` in `packages/agent-service/src/worker/mcp.ts:87-95`: `/(401|unauthorized|sign-in|sign in|auth required|needs auth|oauth)/i`. OMP's HTTP transport formats the failure as `` `HTTP ${status}: ${body} [WWW-Authenticate: …; Mcp-Auth-Server: …]` `` (`.../@oh-my-pi/pi-coding-agent/src/mcp/transports/http.ts:501-517`), so a real `401` matches — but:
  - `403` (many hosted servers answer 403/`insufficient_scope`/bot challenge before OAuth), `404/405/406`, and non-2xx JSON-RPC error bodies produce **no** match → `MCP_APPLY_FAILED` → `saved-not-connected` → **throw**.
  - Any server that answers the handshake perfectly but rejects `tools/list` yields a different failure stage/code.
- In the UI, a thrown/caught result sets `failed = true` and shows `toast.error('Could not install {name}')` with `result.error` as description: `packages/ui/src/components/views/IntegrationsCatalogView.tsx:480-491` (non-`ok` → `failed`), `:551-554`. The `saved-needs-auth` success path (`:493-496`, `:555-556` `toast.info('Sign-in required')`) is **never reached** for a thrown outcome.
- `useMcpConfigStore.mutate` keeps `ok: false` whenever outcome is `saved-not-connected` (`packages/ui/src/stores/useMcpConfigStore.ts:84-90`) and re-publishes the configuration from the error's `details.result` (`:93-100`). So the **server is saved** but the UI still says "Could not install". That is exactly the maintainer's screenshot.

**This is the "direct error instead of a correct prompt"** — the same class of defect the 2026-11-12 research already recorded (`​.workflow/research/feedback-2026-11-12/02-integrations-remote.md`, item 2) and that task 25 was supposed to fix. Task 25 added the `MCP_AUTH_REQUIRED`-exact match (`.workflow/done/ux-feedback-2026-11-12/25-mcp-scope-data-safety.md`) — an evidence check that is stricter than the classification the supervisor uses for live workers (`catalog.ts:531-536` accepts `MCP_AUTH_REQUIRED`, `AUTH_REQUIRED`, and `/401|auth|sign-in|unauthorized/` over code and detail). **The two paths disagree**, and the stricter one is the one without a live worker — which is the common case right after install in a fresh chat.

**Confidence on which server the maintainer used:** the only OAuth server in the real data is **Figma** — `catalog-state.json` workspace `ws_fdf82dc7…` holds `figma` at revision 3 (project scope, `chats/2026-11-10/session-d8720750…/.omp/mcp.json`), and the current chats-root workspace (`ws_8d541005…`) is at revision 4 with `servers: []`. ### F2 (blocking for Figma specifically) — Figma can never complete OAuth: its DCR endpoint rejects OMP, and the fork discards the reason. Confidence: high.

Verified live against the real service:
- `https://mcp.figma.com/.well-known/oauth-protected-resource` → `authorization_servers: ["https://api.figma.com"]`, scopes `["mcp:connect"]`.
- `https://api.figma.com/.well-known/oauth-authorization-server` → `registration_endpoint: https://api.figma.com/v1/oauth/mcp/register`.
- OMP itself documents that Figma's registration endpoint 403s unapproved clients and that the only path is a manual `oauth.clientId` (`.../pi-coding-agent/src/mcp/oauth-flow.ts:441-450`, `#tryRegisterClient` `:660-700`, `#missingClientIdError` `:800-830` — "Only clients listed in the Figma MCP Catalog can connect").

The fork's flow uses that SDK path but **destroys the diagnostic**: `#runOAuthFlow`'s catch passes only `NativeMcpError` instances to `#toOAuthError` and otherwise synthesises `'MCP OAuth authentication failed.'` (`packages/agent-service/src/worker/mcp.ts:913-918`, `:1403-1408`). So the rich DCR message ("…dynamic client registration was rejected (POST …/register → HTTP 403 — unapproved_client)… Configure `oauth.clientId`") is replaced by an opaque sentence. Same for `OAuthIssuerMismatchError` (subclass of `Error`, not `NativeMcpError`) and every token-exchange error. The sign-in panel then shows that generic sentence in red (`packages/ui/src/components/sections/mcp/McpOAuthSignIn.tsx` — `setError` from the catch in `submit`).

### F3 — No anonymous 401 probe before discovery; discovery starts from the server URL, losing the challenge's hints. Confidence: high.

`#runOAuthFlow` goes straight to `discoverOAuthEndpoints(entry.server.transport.url, oauthInput?.issuerUrl, oauthInput?.resourceMetadataUrl)` (`mcp.ts:849-861`) with the user's optional fields only. It never performs the unauthenticated probe that OMP's shared reauth engine does to recover `resource_metadata`, `scope`, and the auth server from `WWW-Authenticate`/`Mcp-Auth-Server`: `.../pi-coding-agent/src/mcp/oauth-reauth.ts:373-450` (`resolveMcpOAuthEndpointsFromServer`), plus `analyzeAuthError`/`extractOAuthEndpoints`/`extractOAuthChallengeScopes` in `oauth-discovery.ts:59-360`. Consequence: servers whose metadata is only discoverable via the challenge (Linear-style `resource_metadata` header, Atlassian path-scoped `/v2/mcp`, Stripe `access.stripe.com/mcp`, Supabase `api.supabase.com`) can fail discovery with `MCP OAuth endpoints could not be discovered.` (`mcp.ts:859`) even though OMP's TUI would succeed. The fork works around this by exposing `issuerUrl`/`resourceMetadataUrl` inputs in the UI, i.e. the user has to know the answer. `discoverOAuthEndpoints` *does* probe `/.well-known/oauth-protected-resource` at the origin/parent (`oauth-discovery.ts:471-680`, note: the supplied `resourceMetadataUrl` is only tried first at `:511-528`), so origin-shaped servers (Notion, Linear, Figma) work; path-scoped ones are the risk.

### F4 — The sign-in is not started by the install, and nothing polls for completion. Confidence: high.

- The pre-install note promises it: `'integrationsCatalog.oauth.note': 'Installing opens the service sign-in in your browser.'` (`packages/ui/src/lib/i18n/messages/integrations-catalog.i18n.ts:82`). It does not. `installEntry` only sets `selectedId` (`IntegrationsCatalogView.tsx:493-518`) and toasts.
- `McpOAuthSignIn` does not auto-start: its start button is only rendered in the non-pending branch (`McpOAuthSignIn.tsx`, "Authorize" button → `submit('start')`). Upstream's flow auto-started for `needs_auth` and passed `autoStart` (`packages/ui/src/components/sections/DOCUMENTATION.md:269-272`, `:258-266`).
- Opening the authorization page is a **third** click ("Open in browser" → `openExternalUrl(pendingFlow.launchUrl ?? authorizationUrl)`).
- No polling: the component reads `GET …/mcp/servers/:id/oauth` once on mount (`McpOAuthSignIn.tsx` effect), and the `complete` POST blocks until the callback arrives or 5 min elapse. With the loopback callback server this "works" only if the same request stays open; the UI has no progress/“still waiting” affordance other than the static text `integrationsCatalog.oauth.waiting`.
- Upstream had a purpose-built completion surface the fork deleted: `packages/ui/src/components/sections/mcp/McpOAuthCallbackPage.tsx`, `startMcpAuthorization.ts`, `mcpOAuth.ts`, plus Host routes `POST/GET/DELETE /api/mcp/auth/pending` and `/mcp/oauth/callback` (upstream `packages/web/server`, cf. `.workflow/done/ux-feedback-2026-11-12/31-repair-settings-sections.md:41-42` which deleted `mcp/useMcpOAuthIntegration.ts` as "spoke the retired OpenCode integration OAuth flow"). Grep confirms the fork has **no** `/api/mcp/auth`, no callback page, no `startMcpAuthorization` — only the canonical `…/mcp/servers/:id/oauth` route (`packages/agent-service/src/supervisor/workspace-routes.ts:258-300`).

### F5 — Platform: the redirect URI listener is the **Agent Service's** loopback, which is wrong for remote/mobile and fragile locally. Confidence: high.

- The callback server binds inside the Agent Service worker process (`MCPOAuthFlow extends OAuthCallbackFlow`; `.../@oh-my-pi/pi-ai/src/registry/oauth/callback-server.ts:155-205`, `:380-450`), default port **3000**, path `/callback`, host `localhost`, random-port fallback allowed only when no client_id is pinned (`.../pi-coding-agent/src/mcp/oauth-flow.ts:196-230` `resolveCallbackOptions`).
- Electron packaged desktop runs the Host and the Agent Service in-process on the user's machine (`packages/electron/main.mjs`, Host spawns Bun service via `agent-service-supervisor.js:443`), so `http://localhost:3000/callback` is reachable by the system browser — **works locally**, but port 3000 is the single most likely busy port (dev servers), and dev servers bound to `*:3000` are exactly the hijack case OMP documents (`callback-server.ts:437-460`). With fallback the redirect URI changes per attempt; providers that validate the redirect against a registered client reject it.
- **Web on a remote Host / mobile Capacitor**: the browser that completes consent is the user's device; the code is delivered to the *Host's* loopback, not the device. The fork's only mitigation is the manual "paste the callback URL" field (`McpOAuthSignIn.tsx` manual fallback), and `MCPOAuthConfigInput.redirectUri`/`callbackPort`/`callbackPath` inputs exist in the contract (`packages/agent-contract/src/catalogs.ts:586-609`) — but nothing computes a redirect that actually reaches the Host. Upstream solved this by writing `buildMcpAuthorizationRedirectUri(name)` = `<Host origin>/mcp/oauth/callback` into the server's config before starting, precisely because "OpenCode falls back to its own loopback … which only works when the browser runs on the same machine" (`/home/shizuku/Project/openchamber/packages/ui/src/components/sections/mcp/startMcpAuthorization.ts:18-40`, `:184-300`).
- `openExternalUrl` on desktop uses `desktop_open_external_url` → `shell.openExternal` (`packages/ui/src/lib/url.ts:157-200`, `packages/electron/main.mjs:4769-4786`); on web it is `window.open(..., '_blank')`. Both fine. Mobile bundles the web UI, so it inherits `window.open` — which on Capacitor opens the system browser, and the callback then lands on Host loopback: broken (F5 second bullet).
- Enterprise boundary: MCP OAuth is currently **not** in the gated list (`packages/web/server/lib/enterprise-mode.js:1-63`), and the Host authorizer allows `mcp-oauth` whenever the server is in the workspace policy (`packages/web/server/lib/host/worker-operation-authorizer.js:138-147`). Per `.agents/skills/enterprise-boundary/SKILL.md` ("a user-initiated action toward a service the user connected themselves (GitHub, Linear) sits outside the mode today; when such an action carries conversation content, raise it with the maintainer") — MCP servers **do** carry conversation content to a user-chosen service, so this is a decision to raise, not silently keep.

### F6 — Non-OAuth credential entries: the install form collects the token, but only via the detail page, and never collects env vars. Confidence: high (UI code), medium (impact).

- `canInstallEntry` **blocks** install until a token is typed for `auth: 'token'` entries unless `tokenOptional` (`IntegrationsCatalogView.tsx:627-640`); `requestInstall` then just opens the detail page (`:654-664`) where the field lives (`:917-938`). That is a prompt, not an error — acceptable.
- The token is written as a workspace credential and referenced via `credentialRef`/`headerCredentialRefs` (`attachMcpToken`, `:436-455`). Fine.
- **Gap:** no catalog entry collects *environment variables* for local servers. The local entries that need them are listed with `auth: 'none'` and no inputs: `grafana` (`uvx mcp-grafana` needs `GRAFANA_URL`/`GRAFANA_API_KEY`) at `packages/ui/src/lib/integrations-catalog/registry.ts:2372`, `mongodb` (`:2341`, needs `MDB_MCP_CONNECTION_STRING`), `terraform`/`azure`/`snyk` etc. Install will succeed and then fail at handshake → `saved-not-connected` → the same error toast as F1, with the child process's stderr as the only clue. The Settings → MCP page *does* have an env/header editor with credential references (`McpPage.tsx:1060-1082`), so the capability exists; the catalog just doesn't surface it.

### F7 — Supply-side risk in F1's fix: `saved-not-connected` is thrown as 503 and also used for `no-active-workers` "connected" (minor). Confidence: medium.

`useMcpConfigStore:84-86` treats `status === 'no-active-workers'` as `applied` even when the coordinator computed `outcome`; and `outcome` is optional in the contract (`catalogs.ts:503-506`). Not a maintainer-visible bug today, but the fix in F1 must not rely on `status` alone.

## 2. Proposed fix

**Owner modules** (no new abstraction; extend the existing ones):

1. **Classification — one rule, both paths.** `packages/agent-service/src/supervisor/catalog.ts`
   - Extract the auth detection currently inlined at `:531-536` into a module function `mcpAuthRequired(outcome)` and use it in `unattendedMcpOutcome` (`:914-925`) instead of the exact-code comparison. Accept `MCP_AUTH_REQUIRED`, `AUTH_REQUIRED`, `MCP_CREDENTIAL_UNAVAILABLE` and the `/401|403|auth|sign-in|unauthorized/` text match on `detail` and `code`.
   - `packages/agent-service/src/worker/mcp.ts:87-95`: extend `isAuthError` to include `403` and `insufficient_scope`, and to treat `cfg.auth === 'oauth'` (already there) plus the catalog's `auth: 'oauth'` marker if carried.
   - Keep `saved-not-connected` a **throw** only for genuinely non-auth failures (that is the invariant "never let fetch failure masquerade as authoritative empty success").
2. **Install must not fail on "needs auth".** `packages/ui/src/components/views/IntegrationsCatalogView.tsx:480-496`: when `outcome === 'saved-needs-auth'` (including when it arrives via `mutate`'s error path), clear `failed`, keep `errorDetail` for the panel, select the detail page, and do **not** toast an error. Toast `toast.info(needsAuth)` as today (`:555-556`) — and change the copy from a claim to a state: `"Figma saved. Sign in to finish."`
3. **Start the sign-in from the install, in the right place.** New state on the detail connection card: `needs-auth → authorizing → connected | failed(reason)`.
   - On `saved-needs-auth` after install, mount `McpOAuthSignIn` with `autoStart` (single method → start immediately, hide the start button; keep it for multi-method, as upstream did at `sections/DOCUMENTATION.md:258-266`).
   - After `pending`, auto-open the authorization page **once** (`openExternalUrl(launchUrl ?? authorizationUrl)`), because the OAuth panel is already the user's explicit intent. Keep "Open in browser" / "Copy link" as fallbacks.
   - Add a **status poll** while pending: `GET …/mcp/servers/:id/oauth` every 1.5 s up to the flow's 5-minute budget, so a completion that arrives on the loopback resolves without the user pressing "Complete authorization". Show elapsed time and a Cancel button. Use `captureRuntimeInstance()` guards, as the component already does for its mount read.
   - On `authenticated`, run `useMcpStore.connect(...)` (already wired) and surface `connected` / the probe detail if it still fails.
   - Keep **Sign out** as the existing `disconnect` action (already implemented in the panel).
4. **Stop destroying the reason.** `packages/agent-service/src/worker/mcp.ts:913-918, 1403-1408`: pass the original `Error` through (`#toOAuthError(error instanceof Error ? error : undefined, …)`), keeping the native code when it is a `NativeMcpError`. DCR rejection, issuer mismatch, token exchange, port-in-use and state mismatch then reach the panel verbatim (OMP already writes them for a reader). For a DCR rejection, also pre-fill the panel's `clientId` field and link the provider's app-registration page — that is the only way Figma works.
5. **Adopt OMP's discovery, not a reimplementation.** In `#runOAuthFlow` (`mcp.ts:836-930`), replace the bare `discoverOAuthEndpoints(url, …)` with OMP's exported `resolveMcpOAuthEndpointsFromServer(config, { authStorage, mcpManager, signal })` from `@oh-my-pi/pi-coding-agent/mcp/oauth-reauth` (`oauth-reauth.ts:373-450`). It does the anonymous probe, `analyzeAuthError`, scope extraction and challenge-driven discovery. Same package, already a dependency, no new abstraction; it also removes the need for the user to supply `issuerUrl`/`resourceMetadataUrl`.
6. **Redirect URI ownership for remote/mobile.** Do not build a second callback server. Add a **Host** callback route in `packages/web/server/lib/host/` — `GET /api/agent/v1/mcp/oauth/callback` (public, no UI bearer, `state` validated against a Host-held pending map, like the existing guest/tracker pattern in `packages/web/server/lib/guests/routes.js:687` and `trackers/routes.js:147`). The UI computes `redirectUri` via a helper equivalent to upstream's `buildMcpAuthorizationRedirectUri(name)` (upstream `startMcpAuthorization.ts:81-88`) and passes it in `MCPOAuthConfigInput.redirectUri`; the Host page then hands the code to `POST …/mcp/servers/:id/oauth { action:'complete', callbackInput }`.
   - Electron **local** (`getRuntimeKey() === 'local'`): keep the Agent Service loopback (it is on the same machine) — but pin `callbackPort` to a dedicated port (e.g. 38471) rather than 3000, and pin `redirectUri` so the URI is stable across attempts.
   - Web (remote Host), mobile, and desktop connected to a remote Host: always use the Host origin redirect. `isDesktopShell()`/`getRuntimeKey()` already exist (`packages/ui/src/lib/runtime-switch.ts:125`).
   - Enterprise mode: raise with the maintainer (see choices); the enforcement point would be the callback route + `resolvePolicy`'s `mcp-oauth` branch, returning `403 enterprise_mode` like provider entry (`canonical-routes.js:273`).
7. **Env-var entries (F6).** Add an `inputs` mechanism for local servers that maps to `envCredentialRefs` instead of tokens: extend `CatalogMcpComponent.local` with `envInputs?: Array<{ id; envName; labelKey; required }>`, render them in `renderSetup` next to the token field (`:893-945`), write values through the existing `canonicalClient.writeWorkspaceMcpCredential` + `updateMcp` path used by `attachMcpToken` (`:436-455`). Populate `grafana`, `mongodb`, `mcp-toolbox`, `azure-devops` (`AZURE_DEVOPS_*`).

## 3. Open choices for the maintainer

**A. What "install" means for an OAuth server**
1. Install saves + immediately starts sign-in (recommended). Matches the existing copy ("Installing opens the service sign-in in your browser") and upstream's `needs_auth` auto-start. Cost: a browser window opens from a click that says "Install".
2. Install saves + shows a big "Sign in" button (no auto-start). Fewer surprises, one extra click, needs the note copy changed.
3. Install saves silently and the catalog pill says "Sign-in required". Cheapest, but recreates the current dead end for anyone who doesn't revisit the detail page.

**B. Where the OAuth redirect lands**
1. Runtime-split (recommended): local desktop/web-on-localhost uses the Agent Service loopback pinned to a dedicated port; remote Host, web-on-remote, and mobile use a Host origin callback route. Correct everywhere, one extra Host route and a pending-state store.
2. Always the Host origin callback route. One code path, works everywhere including mobile, but the Host must be reachable from the browser that consents — not true for a loopback-only Host opened from another machine without a tunnel.
3. Keep the SDK loopback only, and lean on the manual paste field. Zero new surface; keeps remote/mobile broken and keeps the port-3000 fragility.

**C. Enterprise mode and MCP OAuth**
1. Gate it: `mcp-oauth` refused at the Host authorizer and the callback route in enterprise mode (`403 enterprise_mode`), documented in `security.mdx` and the `enterprise-mode.js` gated list (recommended, consistent with provider entry).
2. Leave it ungated as "the user's own third-party service", but record the decision in `.workflow/decisions.md` (it is the maintainer's call; the boundary skill says to raise it, not decide it).
3. Gate only *new* servers and let already-configured ones re-authorize (softer migration, more state).

**D. Figma-class servers (DCR closed)**
1. Keep them in the catalog and surface the client-id requirement with a link to the provider's app registration (recommended). Honest, and the flow is then completable.
2. Drop catalog entries whose DCR is known to be closed (Figma today) until a pre-registered client id ships. Removes a broken promise, shrinks the store.
3. Ship a first-party client id for Figma in the fork. Only viable if the fork registers as an approved Figma MCP client and can keep the secret on the Host — a product/legal decision, not an engineering one.
